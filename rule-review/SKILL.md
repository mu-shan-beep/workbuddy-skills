# 规则与文档一致性审查

## 这个技能解决什么问题

规则类文档（skill、SOP、规范）失效，九成不是写错了某条，而是**同一条事实在几个文件里各说一套**。

典型症状：

- 主规则改了，示例还按旧的写 → 模型照抄示例
- 一处说"能复用就不新建"，另一处说"必须现生成"
- 规则要求"近 4 篇不重复"，但可选范围本来就只剩 2 个且都有前置条件
- 模板括号里写着"来自学情预设"，等于授权编造课堂经历
- 样本表把"实际被封"和"AI 判断可能被封"并列，再从差异推出结论

**共同点：全部是成对／跨文件问题。** 单文件通读、单点 grep 都看不见。

## 触发

- 用户要求审查、检查、读码、复核某个 skill 或规程文档
- 用户问"为什么没查出来""还有没有别的问题"
- **每次修改规则之前与之后**（改前查投影，改后查残留）
- 交付前最后一次文档自检

## 前置门禁：审查 ≠ 修改

> **用户说"查"，默认动作是只读、出报告、等确认。不得在报告前改动被审文件。**

被审文件是证据。就地改写且无备份，等于让"我判断成立"变成无法核对的事——对方没法验证结论是否真成立，也没法比对原始状态。

要动手必须满足其一：
1. 用户明确说"改／修／落地"；
2. 报告已交付，用户点名同意其中若干条。

## 三条核心方法

### 方法一｜按事实查，不按文件查

**检查单位是"事实"，不是"文件"。** 按文件读，每个文件内部都通顺；把同一事实在几个文件里的原文并排读，矛盾才现形。

1. 沿用已有的[事实台账](references/fact-ledger-template.md)，或在审查报告里列临时清单。逐条写对象、适用条件、权威源、同义说法和复述位置。审查委托先在报告内补漏，获授权修改时再回填台账。
2. 从权威源和入口出发，沿引用追到主规则、模板、示例、自检和避坑表。关键词命中和已登记位置都只是起点。逐条并排给出原文及文件行号，区分现行要求、示例、历史记录与反例。
3. 比较同一对象在相同适用条件下的结论。默认值、必做、禁令、例外和授权范围分别读。核对不到的范围如实列出。

事实的典型形态：一句承诺（"课件以可画链接交付"）、一个数字（"标签 10 个"）、一种做法（"正文收尾不写声明"）、一条禁令（"无交付文件不写发货文案"）。

### 方法二｜三类机械检查，筛候选

单点 grep 只回答"在不在"。要发现矛盾，跑这三类：

| 检查 | 做什么 | 能抓什么 |
|---|---|---|
| **同义并列** | 同一对象的所有出现处，打印完整句子 | 同一个承诺在不同文件里的不同说法 |
| **对立检测** | 把 `必须／一律／固定／必写／只能` 与 `禁止／不得／不写／仅` 两类句子各拉一张清单，两两看是否指向同一对象 | "A 说必须复用"对"B 说必须现生成" |
| **可行性验算** | 每条带前置条件的规则，代入一个最坏输入走一遍，看还有没有出口 | 规则把所有路径都堵死 |

候选检索见[检查方法](references/checks.md)。扫描器列出命中、措辞和数字。人工核实原文与条件，并用具体输入走一遍有前置条件的规则，写出仍可用的路径或无解原因。

### 方法三｜承诺回上游核，不继承旧文本

审查或修改**交付物、格式、数量、金额、领取方式、平台机制**等承诺时，打开产出方当前事实源。实际交付物及权限有当次约定时取成品与约定；只有默认流程时标明是默认。

继承旧模板里的说法是错误的主要来源——旧模板当年可能对，上游已经改了。

| 承诺类型 | 回哪核 |
|---|---|
| 交付什么、什么格式、几页几份 | 产出该成果的技能里的交付规程 |
| 平台怎么算、怎么判 | 平台明文规则／官方文档 |
| 样本结论 | 原始样本数据，不看二手转述 |

## 报告格式（硬要求）

每条写清**核对结论、证据来源与把握度**。证据来源区分用户约定、上游规则或成品、平台明文、原始样本或实测、推演与假设。实测结果只能支持它实际观察到的现象。样本归因、平台机制和本地保守约定分别写。

**核对结论**：

| 类型 | 含义 | 处理 |
|---|---|---|
| 已证实 | 有直接对立的原文、上游证据，或可复算的无解输入 | 给出原文和行号，或列明输入与结果 |
| 需验算 | 逻辑上可能无解／越界，但需代入具体输入才能确认 | 附验算过程 |
| 待核 | 需要上游文件、平台规则或用户确认才能定论 | 标明缺什么 |

**把握度**：拿不准就写"不确定"。**把自己的推测写成结论，比漏报更糟**——对方会照着改。

**报告结构**：

1. 一句话结论（存在几类问题、最严重的是哪类）
2. 逐条给出事实及适用条件、并排原文（文件及行号）、权威源或验算过程、核对结论、证据来源、把握度。
3. 列出未核位置、缺失来源与尚未试跑的场景。机器项按实际覆盖范围报告。
4. 修复建议，但**不执行**

## 反模式（全部来自真实失误）

| 反模式 | 后果 |
|---|---|
| 用关键词计数当验证 | "某规则出现 42 次"证明不了规则对不对，只证明它重复 |
| 只验"我改的那处是否落地" | 改完不查投影，示例继续教废止写法 |
| 把审查做成修改 | 证据被就地覆盖，结论不可核对 |
| 样本表混用实测与推测 | 从错误前提推出"差异收敛到三点"这种假结论 |
| 写完规则不做可行性推演 | 规则把所有出口堵死，还叫它"强制" |
| 用"用户没抱怨过"当没问题 | 没被指出的坑会一直留着 |

## 交付前自检

- [ ] 事实清单里的每一条，所有出现处都并排读过
- [ ] 已按对象和适用条件确认对立候选，并把确有冲突的原文写入报告
- [ ] 每条带前置条件的规则都做过最坏输入验算
- [ ] 所有交付类承诺都回过上游事实源
- [ ] 报告每条都标了核对结论、证据来源与把握度
- [ ] **没有改动被审文件**（除非用户明确要求改）
