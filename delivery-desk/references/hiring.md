# 招聘：缺口就是岗位

技能不是写出来的，是**招出来的**。每次发现自己手写同一类东西，就是一次招聘信号。

## 一、什么时候该招（四条触发，命中任一即立项）

| # | 触发 | 判据 |
|---|---|---|
| 1 | **同类构件手写第二次** | 同一段逻辑或同一个构件，在两个产物里各写一遍（例：反复出现的那个小零件） |
| 2 | **同一形态返工第三轮** | 改版不是因为参数错，而是因为"没有现成件可用"（例：同一形态改了四版） |
| 3 | **名录全员接不住，但需求会重复** | 一次性需求可以兜底；会重复的需求必须招人 |
| 4 | **用户点名要一种新形态** | 现有承包商都没有这个交付形态（例：要一种此前没人做过的文件形态） |

## 二、什么时候**不**招（防止技能膨胀）

命中任一就不招，走 `SKILL.md` 红线 3 的兜底并登记：

- 一次性、以后不会再出现的形态；
- 需要的能力本质是"一个新领域的口径"，那该加口径卡，不该加技能；
- 现成承包商只差一点参数适配（改工单即可，别造新轮子）；
- 招进来的维护成本高于它能省的工（比如一年用不到三次的冷门形态）。

> 判断口径：**招的是"会重复的活"，不是"这次想省事"。**

## 三、岗位说明书（招人之前先写这一页）

招聘不是"再写个 SKILL.md"，是先定义这个岗位的边界。四块必须写清：

```markdown
# 岗位：<名字>
## 能接什么（一句话 + 3 个典型场景）
## 不能接什么（划清边界，比"能接"更重要）
## 输入 / 输出契约
- 输入：<参数对象，键名由该岗位自己定>
- 输出：<文件形态 + 必须暴露的接口，例如 {根对象, 设置参数的方法, 锚点表}>
## 验收线（通用基线之外，这个岗位自己的硬指标）
```

**输出契约里必须包含"锚点"**：每个可标注的部件要导出语义锚点（如 `partA` / `partB` / `center`），否则下游每接一次都要手调标注偏移量 —— 那是把成本转嫁给用户。

## 四、造：最小可用版，先跑通一个真实样本

1. 用 `skill-creator-for-work` 建目录（`SKILL.md` + `references/` + `scripts/`），frontmatter 只写 name/description，主文件 <500 行。
2. 只做**一个**能跑通的最小能力，不做全家桶。
3. 拿一个真实样本当场验证：产物要过通用基线、硬指标要手算过。
4. 把"怎么用"写进 SKILL.md 的第一屏（不要让人翻到第三节才知道怎么调用）。

## 五、试单：换一个它没见过的题

用**没参与设计**的同类样本再跑一次。跑不通就是没长成，回炉；跑通才许入名录。

试单要留证据：产物路径 + 基线核对结果 + 一帧截图。

## 六、入名录

在**本域名录**里加一行档案，必须写：

- 能接 / **边界（它接不了什么）** / 接单前必读哪个文件 / 验收线归谁 / 实测状态改成 ✅。

从"待招岗位"表里删掉这一条，或标 `✅ 已招（承包商名）`。

## 七、退役

连续两次接不住同类活 → 名录标 ⚠️ 并写失败点；确认被新承包商取代 → 标 `⛔ 已退役` + 原因。**名录只增不删**，否则下次又会派给它。

---

## 八、岗位说明书实例

通用流程不放实例——实例一定属于某个业务。现装域的实例位置：

- `domains/<业务>/hiring-example.md`（现装的那份是作者环境实录样例，**看结构不看业务与技能名**）

**读实例只看结构（四块 + 契约 + 锚点），不看业务内容。**
