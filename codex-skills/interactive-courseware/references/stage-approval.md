# 逐步确认、整体 UI 与建模预览

本规则来自用户明确要求：建模前先画预览图，简单模型可用 teachable-figures，具体路线由智能体判断，每一步产出先交用户确认，再进入下一步。

## 1. 确认如何执行

- 完成当前阶段的具体产物、自查及必要修正，再展示给用户。不能只描述准备做什么就索要批准。
- 等待明确针对当前产物的认可，例如“这版没问题，继续”。沉默、等待超时、提供材料、内部检查通过都不算用户确认。
- 用户提出修改时留在当前阶段，展示修改后的版本，再等确认。不要边等答复边制作依赖该结果的下一阶段内容。
- 阶段内读取资料、编辑和自查可以连续完成，无需把每个工具调用变成确认点；不能把多个应确认的制作阶段一次做完再补问。
- 过程中的每个建模轮次也适用：体块 → 结构 → 形体 → 材料 → 灯光 → 交互 → 优化。仅执行所选建模路线实际需要的轮次；拟合并或跳过轮次时提前列明，取得用户认可，不能事后补批。上游要求额外门槛时同时遵守。
- 多个不同模型分别有预览与确认记录。不得用确认其中一个模型代替确认全部；用户明确接受一组模型的预览时，才按该组范围执行。
- 本阶段确认只覆盖展示版本与说明范围。实质改变教学结论、外形比例、部件关系或交互规则时，退回相应阶段重新确认；拼写修正等不改变已认可结果的内部修正可在当前阶段完成。
- 用户可以明确授权合并阶段、批量处理或改变确认方式；记录其授权范围，不能从“开始制作”等笼统指令推断放弃逐步确认。
- 用户后续明确授权：问题记录与技能进化由智能体判断是否需要确认，常规维护不逐条打断。按 [优化闭环](improvement-loop.md) 分级处理；此例外不放宽课件设计、预览、模型和交互产物的确认要求。

## 2. 预览必须是实际可见的图

在正式几何建模与界面开发前，必须绘制并展示两类实际可见的图：整体 UI 界面图和建模预览图。可以采用二维 SVG、手绘式构图或生成图片，不能只有文字提示词、未渲染代码或文件名。不能先做3D模型再截图，倒称为建模前预览。

- **整体 UI 界面图为必交产物**：展示完整页面的舞台、导航/场景切换、控制面板、任务、读数、图例与反馈布局，以及配色、文字层级和主要操作入口；只画模型不能替代此项。
- 按实际教学设计绘制默认界面，以及影响布局的关键操作、任务/反馈状态；不同场景结构明显不同时补对应界面。用户要求手机适配时补相应布局，不凭桌面图声称已确认手机界面。没有用到的区域不强行添加。
- 模型图明确对象本身的轮廓、部件、比例、材质和动作；UI 图明确对象与全部操作区域怎样共同呈现。两类图可放同一预览包中，但分别标明版本、范围与待确认点，不能把用户对其中一项的认可推定为对两项都认可。

- 简单模型：至少一张结构与比例清楚的示意，标出关键部件、运动方向和观察任务；存在遮挡或剖面要求时补对应视图。
- 复杂模型：展示主要视角及能消除歧义的侧/背/剖面视图，注明关键轮廓、连接、材质、运动轴与可拆件。视图数量由歧义决定，不为凑数量虚构隐藏结构。
- 需要位图生成时读取 `imagegen` 并使用可用图像生成能力；简单精确的结构示意可以直接绘制并渲染 SVG。生成能力不可用时，交付符合当前细节要求的可见示意，或明确缺项并询问，不假装已生成图片。
- 用户已有图片可以作为资料，但仍整理成适合本次建模的预览并展示；清楚指出保留、补充和推测的部分。
- 预览同时列出建模路线：简单/复杂判断、拟用技能、可交互部件和拟建模轮次。用户确认 UI 图、建模图与方案后，才能开始建模及正式界面开发。纯二维课件也须提供整体 UI、对应结构和关键状态的图示，不强制引入三维模型。

## 3. 预览不是科学证据

生成图仅确定视觉目标，不证明结构或学科知识正确。与教材、可靠参考的冲突先修正，不把生成图当作唯一真值。多个视图需检查轮廓和部件一致性；隐藏结构、示意比例和未知尺寸单列。

建模中持续对照已确认预览与资料。若发现预览无法支持合法结构或实现目标，说明差异、提交新预览，用户确认后再继续，不自行改形。

## 4. 持续工作记录

在课件工作目录维护简短进度记录，可沿用已有项目记录。至少包含：阶段/模型、产物版本与路径、待确认或已确认、用户原话及对应回合、下一步。UI 图与模型图分别记录确认范围；没有明确认可就不能写成“已确认”。恢复任务先核对记录和最近用户消息；不从自己的上次总结推定批准。

当前阶段答复格式：本轮产物（链接或图） → 自查和限制 → 请确认的具体内容 → 确认后的下一步。提出确认后停止依赖工作，不设置自动继续的时间限额。
