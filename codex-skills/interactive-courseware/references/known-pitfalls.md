# 已记录的问题与防范

以下条目来自本次技能设计中用户的直接纠正，是工作约定的依据，不是实际课件运行故障的复查证据；后续根据课件实践补充。

## 索引

| 编号 | 适用阶段 | 问题 | 防范位置 |
|---|---|---|---|
| FLOW-001 | 所有制作阶段 | 自动推进绕过用户逐步确认 | 入口流程、逐步确认规范 |
| MODEL-001 | 建模前与建模中 | 未先画预览，复杂建模仅作为条件可选 | 技能协作、预览规范、建模接口 |
| MAINT-001 | 记录与技能维护 | 将课件逐步确认扩展成每条维护都需确认 | 优化闭环的分级决策 |
| UI-001 | 视觉与建模预览 | 仅预览对象，未绘制整体 UI | 预览规范、设计卡、视觉验收 |
| UI-002 | 课堂投影布局与验收 | 纵向堆叠操作导致滚动、模型被挤占或裁切 | 入口布局原则、制作与验证 |

## FLOW-001：整体制作授权不能代替逐步确认

- 来源：本次用户两次明确要求，每完成一步先展示产物，只有用户确认后才进入下一步。
- 已观察问题：初版技能含“设计信息充分时不增加逐阶段确认”的安排，与用户后续明确要求不符。
- 修改：每阶段实际产物和建模轮次分别展示；记录版本、认可范围和用户原话；修改后重新确认。
- 复查状态：修改稿已对照要求检查；尚未在真实课件生产中验证。
- 下次检查：本阶段是否有实际产物及明确确认；没有则不执行依赖它的下一阶段。

## MODEL-001：先画预览再建模

- 来源：用户要求把建模前预览设为标准流程，简单模型可用 teachable-figures，具体路线由智能体判断。
- 已观察问题：初版将 img2threejs 仅限于用户已有参考图的还原场景，且没有独立的建模前可见预览步骤。
- 修改：所有模型先展示预览与方案并确认；简单模型优先 teachable-figures，复杂精细造型默认 img2threejs，以已确认预览及可靠资料作为输入。
- 复查状态：修改稿已对照要求检查；尚无本项目实际模型的造型验收结果。
- 下次检查：是否已有用户确认的真实可见图、对应版本和建模方案；生成预览不能替代知识依据。

## MAINT-001：常规记录与维护不逐条确认

- 来源：用户明确说明，记录和技能进化由智能体决定是否需要用户判断，不是每项都确认。
- 已观察问题：前一稿把“正式技能更新”统一设为必须确认，多次请求用户批准例行维护。
- 修改：主动记录、复盘、去重、修正执行说明及增加有证据的防范项；改变用户目标、流程或确认规则等重要决定才先确认。
- 复查状态：已核对各引用中的权限表述一致；实际课件制作中的确认执行仍需持续观察。
- 下次检查：先判断影响范围；属于已授权常规维护时自行完成并验证，避免重复询问。

## UI-002：课堂投影以观察和操作便利为先

- 来源：2026-11-05，用户反馈授课时操作影响观察，明确要求将“中间主观察面板、两侧操作”写入技能，避免沿用上下堆叠布局。
- 已验证根因：第一章参考系旧样例在1280×720窗口中页面高1147像素，操作区从文档y=830开始；滚动操作后场景顶部移出视口。400像素常驻侧栏进一步压缩观察区。只检查无横向溢出未能发现该问题。
- 措施：以中间观察、左右操作为默认投影布局；一屏内同时看见实验与常用操作，简短控件分组、内容按需揭示，比例依可用空间调整。
- 下次检查入口：设计预览检查整体区域分工；实际运行按制作与验证中的课堂投影布局检查，覆盖常见720高度及操作后的场景连续性。
- 证据与限制：本项目“课堂布局重设计/旧布局实测.json”及旧布局截图为原故障证据；两侧操作方案为用户明确的设计要求，尚不能声称新版运行可用性已验收。
- 后续用户要求：页面必须响应式，并适配手机。桌面与手机采用不同的控件排布；最小验收视口及触控、旋转检查见正文与制作验证。此项为明确的设计要求，不能写成已完成真机适配的事实。

## 后续记录要求

UI-001：用户明确要求预览阶段同时绘制建模图和整体 UI。此前正式技能第3阶段只列建模预览，整体 UI 尚是建议，容易漏执行。现已将整体 UI 列为必交图，并要求分别记录两类图的确认范围，开发结果对照 UI 图验收。此条是已明确的工作要求，尚未代表实际课件的 UI 可用性验证。

使用稳定编号，新增记录包含：来源问题、适用条件、已验证根因、有效措施、下次检查入口、验证证据与限制。保留失败尝试的必要摘要。合并同根因条目，过期经验按优化闭环判断修订，不无限增长重复规则。
